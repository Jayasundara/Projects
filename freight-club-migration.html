Freight Club Web App & API Migration

Migrated the Freight Club web application and API platform from a two-VM Azure hosting model to Azure App Service, introducing four App Services while preserving Cloudflare as the public entry layer and using Azure Application Gateway as the Azure ingress, filtering and routing tier.

01 / Project Overview

Modernizing application hosting while preserving the edge path.

The Freight Club platform was migrated from Azure Virtual Machine-based hosting to Azure App Service. The legacy design used two Azure VMs for web and API workloads. The completed solution used four App Services: two for the web application and two for the API layer.

Cloudflare remained the external entry point. Azure Application Gateway became the Azure-side ingress and routing layer before requests reached the appropriate App Service backends, while the application and API tiers continued to use the existing database system.

02 / Project Background & Requirements

From VM-hosted workloads to platform-managed application services.

Legacy Challenge

The original web and API workloads depended on two Azure VMs. This kept operating-system maintenance and VM administration within the application support scope.

Migration Requirements

  • Migrate the web application to Azure App Service.
  • Migrate the API workload to Azure App Service.
  • Replace the two-VM hosting design with four App Services.
  • Keep Cloudflare as the external traffic entry point.
  • Route Azure-bound traffic through Azure Application Gateway.
  • Maintain connectivity to the existing database system.

06 / Traffic Flow

Controlled edge-to-application request routing.

1. User RequestEnd Users → Public Application Endpoint

Users accessed the Freight Club platform through its public-facing endpoint.

2. External EdgeInternet → Cloudflare

External traffic first reached Cloudflare, which remained the public entry layer.

3. Azure IngressCloudflare → Azure Application Gateway

Approved Azure-bound traffic was forwarded to Azure Application Gateway.

4. Backend RoutingApplication Gateway → Web App Services / API App Services

The gateway evaluated listeners and routing rules and directed web and API requests to the correct backend tier.

5. Data AccessApp Services → Database System

The application and API tiers connected to the existing database system as required.

07 / Application Gateway Role

Centralized Azure ingress, filtering and routing.

Azure Application Gateway became the central Azure ingress point for the migrated platform. Instead of exposing the individual App Services as the primary external entry path, Cloudflare sent traffic to the gateway, which applied configured listener and routing rules before forwarding requests to the correct web or API backend.

This kept traffic handling centralized and created a clean separation between the public edge path and the application hosting layer.

08 / Cloudflare Integration

Cloudflare remained the external traffic entry layer.

The post-migration request path preserved Cloudflare as the first public-facing layer. Cloudflare forwarded relevant application traffic to Azure Application Gateway, which then routed requests to the appropriate App Service backend.

Users → Cloudflare → Azure Application Gateway → Web / API App Services → Database
09 / Migration Approach

Controlled transition from VM hosting to App Service.

  • Identified the existing web application and API workloads running on the two Azure VMs.
  • Created the required Azure App Services for the web and API tiers.
  • Migrated application code and runtime configuration from VM-hosted workloads to App Service.
  • Configured Azure Application Gateway backend targets and routing for the new App Services.
  • Updated the Cloudflare-to-Azure traffic path to use Application Gateway as the Azure ingress layer.
  • Validated web application access, API connectivity, and database communication.
  • Transitioned production traffic away from the legacy VM-hosted application services after validation.
10 / Technical Summary

A cleaner, platform-managed application hosting model.

The migration moved Freight Club from two Azure VMs to four Azure App Services, separating the web and API hosting tiers. Cloudflare remained at the public edge, while Azure Application Gateway was introduced as the Azure-side ingress and routing layer.

This design reduced dependency on VM-hosted runtimes and operating-system maintenance while establishing clearer separation between edge traffic management, ingress routing, application hosting and the database tier.
